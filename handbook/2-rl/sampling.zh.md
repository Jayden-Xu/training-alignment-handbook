# 采样：可以重放的 token

## 我们在哪里

完成[整个模型](whole-model.md)和[并行](parallelism.md)两步后，一个请求的 logits
不再依赖它的批次、模式或 TP 度。采样器在 logits 之后。要为调试而重放一次 rollout，
同样的 logit 位必须给出同样的 token，不管这个请求和谁一起批处理、是否被抢占、
是否经过投机验证、是否在别处恢复。这一步让采样出的 token 只由这一行本身决定。

## 思路

采样器从一个随机流中取噪声，再选出一个 token。有两样东西会让 token 依赖行以外的东西：

1. **噪声从哪里来。** 整个批次共用一个生成器时，一行的抽样取决于它的行号。
   每个请求一个生成器时，抽样取决于这个请求已经用掉了多少随机流。设想一个请求
   为 token 1–3 抽了噪声 u1、u2、u3，然后被抢占并重算：如果它的生成器从种子重新开始，
   token 4 又会拿到 u1；如果生成器保留，回滚 token 3 时，token 3 会拿到 u4。
   无论哪种，某个位置的噪声都变了。其他请求的 n > 1、投机块的大小、在新进程中重启，
   都会以同样的方式让它移动。
2. **概率怎样求和。** top-p 需要对排序后的词表做累加和。对长行做累加和是一种归约，
   GPU kernel 按形状选择它的顺序；其中一个位的变化就会移动 nucleus 的边界。

所以每个请求一个随机流是批不变的，但不可重放。规则：用 token 本身是什么
（种子、位置、用途、样本序号）来确定噪声，而不是用之前抽过多少次；并且让每个求和都精确。
原理和 kernel 一样：结果只能依赖这一行自己的数据。

| 组成部分 | 原生形式 | 可重放形式 |
|---|---|---|
| 噪声 | 有状态的生成器，共享或每请求一个 | 基于计数器：每个（种子、位置、用途、流）一个均匀数，没有状态 |
| 求和 | 浮点 softmax 和累加和 | 整数权重，因此每个求和都精确 |
| 顺序 | 不稳定排序 | （值降序、下标升序），稳定 |
| 投机解码 | 草稿消耗随机流的方式影响之后的抽样 | 草稿 token 当且仅当等于目标模型自己的样本时才接受 |

用精确相等来验证时，投机解码在每个块大小下都给出和不用草稿解码完全相同的 token。

## 步骤

1. **找出你的引擎采样器依赖什么。**
   - 目标：一个请求的 token 依赖它的邻居或历史的所有方式。
   - 做法：阅读引擎的采样器：生成器在哪里创建、每个请求每步抽多少噪声、
     抢占时发生什么、top-p 怎样求和；[报告](../../examples/sampling/REPORT.md#what-the-engines-do-read-from-source-not-run)
     里有对两个引擎的这种阅读。
   - 成功标准：每种依赖都有名字。
2. **在重放的两侧都使用基于计数器、精确求和的采样器。**
   - 目标：token 只由 logit 位、种子、位置、用途、流和采样参数决定。
   - 做法：参考采样器 [tools/bi_sampling.py](../../tools/bi_sampling.py)
     （`sample`、`spec_verify_exact`、`spec_verify_rejection`）。
   - 成功标准：在批处理、带重算和回滚的抢占、分块投机、新进程中恢复之后，token 都相同。
3. **检查它采样的是正确的分布。**
   - 目标：不变，而且没有偏差。
   - 做法：用卡方检验把经验频率和独立计算的目标分布比较，再用一个故意错误的目标作对照。
   - 成功标准：对真实目标不拒绝，对错误目标明确拒绝。

| 选项 | 得到什么 | 代价类别 | 何时选择 |
|---|---|---|---|
| 共享随机流 | 不可重放；抽样取决于行号 | 免费 | 需要重放时永远不要用 |
| 每请求一个生成器 | 批不变；在抢占、回滚、其他请求的 n、投机解码、重启时失效 | 免费到小 | 只重放简单、不被打断的请求 |
| 基于计数器、整数权重的采样器 | 在测过的每种调度下都可重放 | 大批次时中等（不到 2x）；在噪声融合进 kernel 之前，小批次时大（2x 或更多） | 任何你可能需要重放的 rollout |
| 同上，使用多项式 exp | 在 CPU 和 GPU 之间也相等 | 相对默认 exp 从免费到大（2x 或更多），随批次增长 | 在另一种设备上重放 |

已证明：参考采样器在批处理、抢占、回滚、投机解码和恢复下达到 L1–L3，
并且采样的是预期的分布；在一种 GPU 型号上、用一个玩具引擎
（[报告](../../examples/sampling/REPORT.md#results)）。尚未证明：
打过补丁的生产引擎、min-p、beam search、CUDA graphs、bf16 logits。

## 可能出错的地方

!!! warning "累加和是薄弱环节"
    对词表做的浮点累加和会随批大小变化，对一个长行甚至在多次运行之间都不确定。
    提高精度不能固定顺序。用整数权重让求和精确。

!!! warning "从种子重新创建生成器"
    引擎常常在请求重新进入 prefill 或新进程时，从种子重建它的生成器。
    随机流从头开始而 token 继续往后，于是之后的每次抽样都变了。
    改用位置确定噪声，或者保存生成器的状态。

!!! warning "其他请求的 n 会改变你的抽样"
    按批次中最大的 n 填充噪声的引擎，会让每个带种子的请求的随机流前进这么多。
    这样一个请求的 token 就取决于它和谁一起批处理。只按（请求、样本序号）抽样。

!!! warning "拒绝采样让 token 依赖草稿"
    经典的投机规则可以复现，但它的 token 依赖草稿模型。如果重放不能依赖投机解码，
    就用与目标模型自身样本是否相等来验证，并接受更低的接受率。

!!! warning "两种 exp 实现就是两个采样器"
    库函数 exp 和手写的多项式给出不同的权重，CPU 和 GPU 的库函数 exp 之间也不同。
    每个部署选一种并保持不变。

## 小结

- 每个请求一个随机流是批不变的，但不可重放。
- 用（种子、位置、用途、流）确定噪声；没有状态，也就无需恢复。
- 用整数权重让对词表的每个求和都精确，用下标打破平局。
- 用与目标样本是否相等来验证投机解码，让它不留痕迹。
