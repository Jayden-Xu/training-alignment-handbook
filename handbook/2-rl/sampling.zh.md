# 可重放的采样

## 我们在哪里

完成[整个模型](whole-model.md)和[并行](parallelism.md)两步后，一个请求的 logits
已经不再依赖它所在的 batch、推理模式或 TP 规模。采样器接在 logits 后面运行。调试时要重放
一次 rollout，就要求逐 bit 一致的 logits 一定采出同样的 token：不管这个请求和哪些请求
在同一个 batch 里，也不管它有没有被抢占过、有没有经过 speculative decoding 的验证、
是不是换到别的机器上恢复的。
这一步让采样出的 token 只由这一行本身决定。

## 思路

采样器从一个随机流里取出噪声，再用它选出一个 token。有两件事会让 token 依赖这一行
以外的东西：

1. **噪声从哪里来。** 如果整个 batch 共用一个生成器，一行取到的噪声就取决于它的行号。
   如果每个请求各有一个生成器，噪声就取决于这个请求已经用掉了多少随机流。设想一个请求
   为 token 1–3 依次取了噪声 u1、u2、u3，然后被抢占并重新计算。如果它的生成器从种子
   重新开始，token 4 会再次拿到 u1；如果生成器保留下来，而 token 3 被回滚，新的
   token 3 就会拿到 u4。无论哪种情况，某个位置上的噪声都变了。同一个 batch 里另一个
   请求的 n > 1、换一个草稿长度、在新进程里重启，也都会这样让噪声错位。
2. **概率怎样求和。** top-p 需要对排好序的词表做累加和。对一个很长的行做累加和，
   本身就是一次归约，GPU kernel 会根据形状来选择它的顺序；其中只要差一个 bit，
   nucleus 的边界就可能移动。

所以，每个请求一个随机流虽然是 batch-invariant 的，却不能重放。规则是：噪声要由这个 token
本身是什么来决定（它的种子、位置、用途和样本序号），而不是由之前已经抽过多少次来决定；
同时，每一次求和都必须是精确的。这和 kernel 的原理相同：结果只能依赖这一行自己的数据。

| 组成部分 | 原生形式 | 可重放的形式 |
|---|---|---|
| 噪声 | 有状态的生成器，整个 batch 共用一个，或者每个请求一个 | 基于计数器：每个（种子、位置、用途、流）对应一个均匀随机数，没有状态 |
| 求和 | 浮点的 softmax 和累加和 | 使用整数权重，因此每次求和都是精确的 |
| 顺序 | 不稳定的排序 | 稳定的顺序：先按值降序，再按下标升序 |
| speculative decoding | 草稿模型用掉了多少随机流，会影响之后的抽样 | 草稿 token 当且仅当等于目标模型自己采出的 token 时才被接受 |

如果用精确相等来验证，无论一次草稿多少个 token，speculative decoding 给出的 token 都和
不用草稿模型、直接 decode 的结果完全相同。

## 步骤

1. **弄清楚你的引擎的采样器依赖什么。**
   - 目标：列出一个请求的 token 依赖同一个 batch 里的其他请求、或依赖自身历史的所有方式。
   - 做法：阅读引擎的采样器，记下生成器在哪里创建、每个请求每一步取多少噪声、
     被抢占时会发生什么、top-p 怎样累加概率；[报告](../../examples/sampling/REPORT.md#what-the-engines-do-read-from-source-not-run)
     里有对两个引擎做的这种分析。
   - 成功标准：每一种依赖都被明确指出。
2. **原始运行和重放都使用基于计数器、求和精确的采样器。**
   - 目标：token 只由 logits、种子、位置、用途、流和采样参数决定。
   - 做法：使用参考采样器 [tools/bi_sampling.py](../../tools/bi_sampling.py)
     （`sample`、`spec_verify_exact`、`spec_verify_rejection`）。
   - 成功标准：在 batching、带重算或回滚的抢占、分块的 speculative decoding、在新进程中恢复这些情况下，
     token 都保持不变。
3. **检查它采样的分布是否正确。**
   - 目标：采样器满足不变性，同时没有偏差。
   - 做法：用卡方检验，把观察到的频率与独立算出的目标分布比较；再放一个故意错误的
     目标分布作为对照。
   - 成功标准：检验不拒绝真实的目标分布，并明确拒绝错误的那个。

| 选项 | 能得到什么 | 代价等级 | 什么时候选 |
|---|---|---|---|
| 整个 batch 共用一个随机流 | 无法重放；抽样取决于行号 | 免费 | 只要需要重放，就不要用 |
| 每个请求一个生成器 | 是 batch-invariant 的，但遇到抢占、回滚、其他请求的 n、speculative decoding 和重启都会失效 | 免费到小 | 只用来重放从未被打断的简单请求 |
| 基于计数器、使用整数权重的采样器 | 在测过的每种调度下都能重放 | batch 大时为中等（不到 2 倍）；在把噪声生成融合进 kernel 之前，batch 小时为大（2 倍或更多） | 任何你可能需要重放的 rollout |
| 同上，再改用多项式实现的 exp | 在 CPU 和 GPU 之间也相等 | 相对默认的 exp，从免费到大（2 倍或更多），随 batch 增大而增加 | 需要在另一种设备上重放时 |

已证明：参考采样器在 batching、抢占、回滚、speculative decoding 和恢复下都达到 L1–L3，
而且采样的是预期的分布。这是在一种 GPU 型号、一个玩具引擎上得到的（[报告](../../examples/sampling/REPORT.md#results)）。
尚未证明：打过补丁的生产引擎、min-p、beam search、CUDA graph，以及 bf16 的 logits。

## 可能出错的地方

!!! warning "累加和是最薄弱的一环"
    对词表做的浮点累加和会随 batch size 变化；对一个很长的行，它甚至在多次运行之间都不确定。
    提高精度也固定不了顺序。要用整数权重，让求和变得精确。

!!! warning "用种子重新创建生成器"
    请求重新进入 prefill 或换到新进程时，引擎常常用它的种子重建生成器。于是随机流
    从头开始，token 却在接着往后生成，之后的每一次抽样都变了。要么改由位置决定噪声，
    要么保存生成器的状态。

!!! warning "别的请求的 n 会改变你的抽样"
    有的引擎按 batch 里最大的 n 来生成噪声，这会让每个带种子的请求的随机流都前进这么多。
    这样一来，一个请求的 token 就取决于它和哪些请求在同一个 batch 里。只按（请求、样本序号）
    来抽样。

!!! warning "拒绝采样让 token 依赖草稿模型"
    speculative decoding 经典的拒绝采样规则是可以复现的，但它给出的 token 依赖草稿模型。
    如果重放不能依赖草稿模型，就只在草稿 token 等于目标模型自己采出的 token 时才接受它，
    同时接受由此带来的更低接受率。

!!! warning "两种 exp 实现就是两个不同的采样器"
    库函数 exp 和手写的多项式 exp 给出的权重不同，CPU 和 GPU 上的库函数 exp 之间也
    不同。每个部署选定一种，并且一直用它。

## 小结

- 每个请求一个随机流，是 batch-invariant 的，但无法重放。
- 用（种子、位置、用途、流）决定噪声。没有状态，也就不需要恢复什么。
- 用整数权重让对词表的每一次求和都精确，值相同时按下标排序。
- 验证草稿 token 时只看它是否等于目标模型自己的样本，这样 speculative decoding 就不会在 token 上留下任何痕迹。
