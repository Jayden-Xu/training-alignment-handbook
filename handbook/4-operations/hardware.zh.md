# 硬件覆盖：哪些因素会改变比特，怎样认定新硬件

本手册的每一条逐位结论，都只在证明它的那个软件栈上成立。换了 GPU、驱动或库之后，
[回归套件](regression.md)会告诉你哪些仍然成立。本页讲哪些软件栈属性会改变比特，
为什么不应期望两代 GPU 一致，以及怎样认定新硬件。

## 概念

在 GPU 上把 4,096 个数加起来：SM 多的 GPU 上，库可能把它们分成很多份部分和；SM 少的 GPU 上，
可能分成较少几份。每种分法在不同的地方舍入，所以即使源码和输入相同，总和的最后一位也可能不同。
规则是：**凡是决定一次归约怎样切分、按什么顺序、在哪里舍入的东西，都是软件栈的一部分；
一个逐位结果属于它的软件栈。** 这和 batch-invariant 是同一条原则，只是高了一层：
那里是 batch 选了 kernel，这里是机器选了 kernel。

## 哪些因素会改变比特

| 属性 | 怎样改变比特 |
|---|---|
| 架构 | 每一代都有自己的矩阵指令，没有任何保证说各代的累加顺序或中间精度相同。库为每个架构提供不同的 kernel，有些 kernel 或数值格式只在较新的一代上存在。Triton 按架构编译，同一份源码会变成不同的机器码。 |
| SM 数量 | 库根据 SM 数量选择 kernel、tile 和 split-K；归约和随机数 kernel 根据它确定 grid 大小。同一架构、SM 数量不同的两种 GPU 可能不一致。 |
| 驱动 | 在测得的扫描里，库相同、驱动版本不同的两组给出了相同的比特；驱动仍然是基线键的一部分，因为它带有 CUDA 的一部分。 |
| CUDA 构建与库 | cuBLAS、cuDNN 和 NCCL 每个版本选的 kernel、算法和协议都可能不同；torch 会改变一个算子用哪个后端（例如 SDPA）。 |
| 互连 | NCCL 根据拓扑和消息大小选择算法（Ring 或 Tree）和协议，而算法决定集合通信的求和顺序。 |

能够延续下去的，是归约顺序写在源码里、不依赖设备的 kernel：手册的 Triton kernel 在同一代、
SM 数量相差很大的两种 GPU 上给出了相同的比特，而原版 GEMM、大规模归约和随机数流没有。
这些 kernel 在另一种架构上是否给出相同的比特，**未测试**。实测：见
[测得的覆盖范围](../../suite/COVERAGE.md#same-bits-on-two-gpus-of-one-generation)。

跨代的逐位一致是不应期望的。一个已报告的例子：DeepSeek-V3 技术报告（arXiv 2412.19437）
说明较新 tensor core 上的 FP8 GEMM 累加只保留有限的精度，所以它每隔固定间隔把部分和提升到 CUDA core 上累加。
因此要在每个软件栈上验证每个不变性级别（L1–L5），跨代相等只有测过之后才能声明。

## 认定新硬件

**目标：** 知道哪些结论在新软件栈上成立，哪些原版行为不同。
**成功：** 新软件栈的一个经过审查的基线已经提交；每一处差别要么是记录下来的特定软件栈上的原版结果，要么是报告出来的发现。

1. 按[回归中"新硬件"一节](regression.md#new-hardware)的说明，用 `--vs-committed` 以 full 模式运行回归套件
   （[tools/bi_suite.py](../../tools/bi_suite.py)）。
2. 用 `--cross-group-info` 对照已提交的 golden 文件运行 SDC 扫描
   （[tools/sdc_scan.py](../../tools/sdc_scan.py)）：它作为参考信息显示，
   哪些算子族与已测过的软件栈给出相同的比特。
3. 每一项失败的必需检查都是一个发现：报告它。每一个现在通过了的有记录的原版失败，
   都是一处要记在它的专题页面上的变化，并写明新的软件栈。
4. 记录基线，并把这个软件栈加到[测得的覆盖范围](../../suite/COVERAGE.md#what-was-measured)。

| 选项 | 得到什么 | 代价等级 | 什么时候选 |
|---|---|---|---|
| 套件，quick 模式 | 缩小尺寸下的每一条结论 | 小 | 先看一眼，或小的库更新 |
| 套件，full 模式加 `--vs-committed` | 写页面时所用的尺寸，以及哪些变了 | 大 | 新 GPU、新架构、发布前 |
| SDC 扫描，跨组 | 哪些算子族与已测的软件栈逐位一致 | 小 | 新 GPU，用来看哪些东西可以跨机器比较 |

## 未测试

这里要把两件事分开。**OpGuard 本身**（捕获、fingerprint、首个分歧点比较）已经在下列平台上用于
生产环境的 LLM 训练，这是它的作者报告的（[OpGuard 论文](https://www.usenix.org/conference/osdi26/presentation/zhou-ziming)）。
**本手册自己的测量**（batch-invariant kernel 和修复、固定的集合通信树、引擎一致性的搭建）
来自同一代 GPU，节点内走 PCIe，两个节点之间走普通以太网，在这些平台上尚未证明：

| 范围 | OpGuard | 本手册的 kernel、修复和搭建 |
|---|---|---|
| 其他 GPU 架构、其他加速器 | 已用于生产（据报告） | 未测试 |
| FP8 tensor-core GEMM 及其提升间隔、NVFP4 | 已用于生产（据报告） | 未测试（FP8 缩放因子是模拟的） |
| 其他 GPU 架构上较新的注意力 kernel（FlashAttention 3、FlashMLA、FlashInfer） | 已用于生产（据报告） | 未测试 |
| NVLink、NVSwitch、NVLS；RDMA、InfiniBand、RoCE | 已用于生产（据报告） | 未测试；固定的集合通信树只在 PCIe 和以太网上证明过 |
| 两个以上节点 | 已用于生产（据报告） | 未测试；在两个节点上成立的固定 Tree 在三个节点上未必成立 |
| 其他 torch、Triton、NCCL 和 CUDA 版本 | 已用于生产（据报告） | 未测试，跨引擎案例里 vLLM 自带的软件栈除外 |

所以在这样的平台上，照常用 OpGuard 定位；依赖本手册的任何不变性结论之前，先用套件重新验证。
按结果文件列出的具体软件栈见[测得的覆盖范围](../../suite/COVERAGE.md)；
完整的待办列表见[待办事项](../open-items.md)。

## 哪里会出错

!!! warning "以为比特会自动延续"
    新 GPU 看起来像更快的旧 GPU，但它的库会选别的 kernel。
    没测就沿用的结论，在它上面可能是错的。依赖任何逐位结论之前，先跑套件。

!!! warning "用原版算子跨机器比较"
    两种不同的机器跑原版 GEMM 或随机数 kernel，可能在哪里都没有 bug 的情况下不一致。
    跨机器只比较顺序固定在源码里的算子，或者让每台机器只和自己比较。

!!! warning "在新硬件上把失败调没"
    必需检查在新硬件上失败，是关于这种硬件或它的库的一个发现。
    用容差把它藏起来，会让这个软件栈上之后的每一条结论都不可信。请报告它。

## 小结

- 一个逐位结果属于它的软件栈：架构、SM 数量、驱动、CUDA 构建、库、互连。
- 不应期望跨代 GPU 逐位一致；声明之前先测。
- 归约顺序固定在源码里的 kernel，才是可能延续下去的那些。
- 用 full 模式的套件和 SDC 扫描认定新硬件，然后记录基线。
